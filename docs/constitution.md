## Article 1: Correctness first

1.1 **(W9)** The package's symmetric trimmed mean is trusted only when it **agrees with R's
`mean(x, trim)` on the same bytes**, by a rule written in the spec before measuring. R's computation is
deterministic, so the target is **exact agreement** (identical float64), with the conditions it assumes
(platform, R version, integer or double input) stated. A tolerance is a fallback only, and only one measured
in a spike (L-W8-04). A program makes the comparison. **[T]**
1.2 **(W9)** R's definition is learned **by running R**: how many observations are trimmed
(`floor(n * trim)`, including its floating-point behaviour), what happens at `trim >= 0.5`, negative trim,
missing values and empty input. Where the package deliberately differs from R (for example rejecting a
negative proportion that R silently ignores), the difference is a requirement, tested, and stated in the
README. **[T][Doc]**
1.3 Asymmetric trimming has no R built-in. Its definition is written in the spec, tested on hand-computed
cases, and cross-checked against the same definition evaluated in R; the README says it is our definition. **[T]**
1.4 Every number in the README (tables and headline) is generated by script from saved results; prose that
cites them is re-checked whenever results change. **[Doc]**
1.5 Statistical code is tested against **answers known independently of the code**: hand-computed small
cases, closed-form values, and R's saved output. **[T]**

## Article 2: Idiomatic, readable Go (McConnell 2004, ch. 32) **[C]**

2.1 Go modules; `gofmt` and `go vet` clean.
2.2 Meaningful, specific names; not abstract, not overly long.
2.3 No useless temporary variables or intermediate results.
2.4 Functions do one thing; large blocks become small, named functions.
2.5 Plain `if/else` and `for`; distribute the NOT in complex Boolean expressions.
2.6 Every exported identifier has a doc comment; comments explain *why*.
2.7 Errors are returned and handled; **no `panic`** for bad input (empty data, NaN, out-of-range
proportions, too many proportions).
2.8 **(W9)** The package **never changes the caller's slice** (it sorts a copy), and is safe for
concurrent use because it holds no state.

## Article 3: Test-first, measured **[T]**

3.1 Failing test before implementation of every critical component; **mutation check** important tests with
`go test -count=1`; a mutation that only breaks compilation does not count (L-W6-14, L-W8-03).
3.2 Standard `testing`; table-driven; tests need neither the internet nor R: R's results enter the Go tests
as **saved files with provenance**.
3.3 Benchmarks with `testing.B` and allocation reporting (`-benchmem`) for the package; a CPU and memory
profile of the program on the largest committed sample; the program logs what it did (structured, to
standard error).
3.4 **(W9)** Runnable **`Example` functions** document the package API and are checked by `go test`.
3.5 Guards, scripts and acceptance checks are themselves tested on a passing and a failing case; exit codes
are tested on the **built binary**, never through `go run`.

## Article 4: Clean, reusable design **[D]**

4.1 **(W9)** The trimmed mean is a **stand-alone, importable module** (`github.com/mioluigi/trimmedmean`)
with **no dependencies outside the standard library**, no printing, no logging and no `os.Exit`. One generic
API serves integers and floats.
4.2 **(W9)** The package is **versioned**: released by a semantic-version Git tag, so that `go get` fetches an
exact, verifiable version. A released tag is never moved.
4.3 The program repository is a thin layer: read data, validate input, call the package, report.
4.4 Pin every dependency version (`go.mod`, `go.sum`); `go.sum` is generated on Luis's Mac. **Never commit
`go.work` or a `replace` line** pointing at a local copy (L-W7-06). The R version is recorded with the results.

## Article 5: Documentation and Git hygiene **[Doc]**

5.1 **(W9)** **Each repository has a complete `README.md`.** The package's: what it computes, its exact
definition, install (`go get`), use (import and call), errors, limits, tests, licence. The program's: roles of
programs and data, getting and using the package, building, running, testing, the Go-versus-R results,
limits, GenAI Tools.
5.2 One task per commit, message starts with the task ID; specs, plan, tasks, reviews, decisions in the
program repository.
5.3 README **GenAI Tools** section (Claude Pro with Claude Code as builder; Gemini Ultra as reviewer); AI
dialogs in `docs/ai-dialogs/` with a `README.md` index.
5.4 `scripts/acceptance.sh` is committed and passes on **fresh clones of both repositories** before
submission, including a real `go get` of the released tag. Checks that need R say so and are skipped with a
clear message where R is absent, never silently.

## Article 6: A finished, friendly application **[A]**

6.1 The README gives **instructions for creating** a macOS binary, a Windows `.exe` and a macOS `.app`, and
the scripts that do it.
6.2 The program **runs to completion with no arguments** on the committed samples.
6.3 User input (data file, trimming proportions) is validated; bad input yields a clear message and a
non-zero exit code.
6.4 A finished run tells the user, in plain words, what was computed, from which data, and how it compares
with R's saved result where one exists. Logs go to standard error.

## Article 7: How we work with AI tools

7.1 Claude Code is the only tool that writes files in these repositories during a task.
7.2 Gemini (web) reviews the spec and the finished repositories; it lists the files it **received** first,
then must cite file and section for every claim.
7.3 Luis approves spec, plan and tasks, and reads every diff before it is committed.
7.4 If implementation shows the spec is wrong, update the spec first.
7.5 Every review finding gets a recorded decision with a reason; testable claims are tested first.
7.6 Spike before planning; predictions state their conditions and are checked and corrected in writing.
7.7 Claude verifies every hand-off and push landed before building on it; after a scripted edit, it checks
the change is in the file before committing (L-W8-11).

## Article 8: Data and privacy

8.1 Inputs and fixtures pass the data gate (`scripts/check-inputs.sh`) before their first commit.
8.2 No personal data in committed files: no e-mail address, user name, host name or home-directory path in
saved results or machine descriptions. (Commit metadata follows Luis's usual Git identity.)
8.3 Samples are **generated by a committed, seeded R script** and committed with a manifest (size, SHA-256,
generator, seed), so R and Go provably read the same bytes. Values are written with 17 significant digits so
that every float64 survives the round trip exactly.
8.4 Luis decides any history rewrite; it touches only our own commits.

## Article 9: Respect for external systems **(W9, adapted)**

9.1 The program calls **no external system at run time**.
9.2 **(W9)** The Go module proxy and checksum database are external systems we publish to: a version is
published once, by tag, from Luis's Mac; nothing is retracted or retagged to hide a mistake (a mistake gets a
new version).
9.3 **R is the reference, not the opponent**: its behaviour is learned by running it, and differences are
reported, not hidden.
9.4 **(W9)** The tutorialspoint instructions are followed where they agree with current Go modules practice;
where they rely on GOPATH, we use modules instead and say why in the README.
