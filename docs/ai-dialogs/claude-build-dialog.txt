     One function covers every case. trimmedmean.Mean(values, proportions...)
     works on any integer or float slice. With no proportion it gives the ordinary mean, with
     one it trims symmetrically, with two it trims low and high separately, and more than

     We differ from R in a few places, and say so. R silently ignores a negative trim and

     R’s behaviour is confirmed by running it:
          It trims floor(n × trim) values from each end, so 100 × 0.29 trims 28, not 29.
          A negative trim is silently ignored, and a trim of 0.5 or more returns the median.
          NA in the data gives NA, empty data gives NaN, and a two-number trim is an

     Two predictions failed, and both changed the design:
          R averages integers with one exact sum divided by n, but doubles with a two-pass
          method, so the same numbers can give different last digits. The package will do
          the same, and that reproduces all 42 integer rows exactly.
          R doesn’t overflow on very large values: it has a fallback, which the package
          copies.
     Floats can’t match R to the last bit once they’re trimmed. R sums the kept values in
     the order its partial sort leaves them, which gives a gap of at most about 2 machine
     epsilons (4.7×10⁻¹⁶ relative to the size of the kept values). The rule is therefore:
          exact agreement for integers, untrimmed data and asymmetric rows;
          for trimmed floats, exact agreement with R’s own fully-sorted mean, plus a
          tolerance of 10⁻¹⁴ against R’s built-in (20 times the measured gap).
     The earlier read-back failure is explained. R’s number parser misread about 27% of the
