4. Domain risks
 ●​ Severity: High — Trimmed mean definition, floor(n * p), and asymmetric definition
 ○​ Where: specs/001-trimmed-mean/spec.md §3 (Definitions), §4 (FR-2, FR-5), §9 (AC-1,
    AC-2, AC-6); docs/spikes/001-environment-and-r-reference.md (§3 P1, Addendum B)
 ○​ Problem: dropLow = floor(n * low) and dropHigh = floor(n * high) in float64 (as in 100 *
    0.29 = 28.999999999999996 → 28) can drop asymmetric counts even when low == high
    if float64 rounding differs, and for asymmetric trimming (low != high), dropLow and
    dropHigh are computed independently from n. If n is small (e.g., n = 2 with low = 0.4, high
    = 0.4), floor(2 * 0.4) = 0 on both ends, which is fine, but if low + high approaches 1.0 (e.g.,
    low = 0.49, high = 0.49 on n = 100), 2 * floor(49) = 98 leaves 2 elements, whereas on n = 1
    with low = 0.49, high = 0.49, floor(0.49) = 0 leaves 1 element. The spec does not state a
    requirement for low + high < 1.0 when two proportions are passed.
○​ Suggested change: A test can verify dropLow and dropHigh against
    math.Floor(float64(n) * p) for n = 0..105 and proportions including 0.29, 0.05, 0.1, 0.2, and
    0.4999, asserting 0 <= dropLow, 0 <= dropHigh, and dropLow + dropHigh < n for valid
    inputs.
●​ Severity: High — Integer vs. float paths, precision, and comparison rule / tolerance
   (§7)
○​ Where: specs/001-trimmed-mean/spec.md §3 (Definitions), §4 (FR-1, FR-4), §7
    (Comparison rule with R), §8.1 (Boundaries);
    docs/spikes/001-environment-and-r-reference.md (§3 P3–P6, Addendum B)
○​ Problem: In Go, int is 64-bit on 64-bit platforms (int64 max ~9.22e18), whereas float64
    has 53 bits of significand precision (2^53 ≈ 9.007e15). Converting large integers (> 2^53)
    or summing values in float64 loses precision, and R's integer mean() uses a single sum
    (numeric in R is float64, so sum(x)/n in R can overflow or lose precision differently from
    Go's float64 accumulation). Also, in §7, "exact agreement with R's mean of the fully
    sorted kept values" for trimmed symmetric float rows may fail by 1–2 ULPs if Go's float64
    two-pass summation order or overflow fallback differs by even 1 ULP from R's full-sort
    mean on aarch64-apple-darwin.
○​ Suggested change: A test can compare Go's output on
    testdata/r-reference/trimmed-means.tsv and *-as-read-by-r.txt against R's values,
    asserting 0 ULP difference on integer, untrimmed, and asymmetric rows, and asserting
    |Go - R_builtin| <= 1e-14 * mean(|kept|) (and checking ULP difference against R's full-sort
    reference) on symmetric trimmed float rows.

6. View on open decisions Q1–Q7
 ●​ Q1 (API shape — variadic Mean(values, proportions...)): Agree with the
    recommendation. It directly matches 0, 1, or 2 trimming proportions and returns
    ErrProportionCount for > 2, keeping a single entry point for callers.
 ●​ Q2 ("Integers and/or floats" — generics [T Number]): Agree with the
    recommendation. A generic constraint over Go integer and float types preserves
    compile-time type safety and avoids any type assertions, while converting a mixed
    collection to []float64 at the call site is idiomatic in Go.
 ●​ Q3 (Infinite values — allow ±Inf, reject NaN or infinite result with ErrNotFinite):
    Agree with a condition: allow ±Inf inputs when they are trimmed or cancel/resolve to a
    finite value, and return ErrNotFinite whenever the resulting trimmed mean is NaN or ±Inf.
    Ensure §4 (FR-4) and §8.1–§8.2 state this consistently.
 ●​ Q4 (trim >= 0.5 — reject with ErrProportion): Agree with the recommendation.
    Returning a median from a function named Mean is surprising in Go; returning
    ErrProportion with a clear message noting R's median behavior satisfies both safety and
    transparency (1.2, §8.2).
 ●​ Q5 (Asymmetric flag syntax — -trim "low,high"): Agree with the recommendation. A
    single -trim flag accepting either "p" or "low,high" mirrors the variadic Mean signature
    cleanly and keeps CLI flags minimal.
 ●​ Q6 (First release version — v1.0.0): Argue for v0.1.0 (or v1.0.0 only after R2 sign-off)
    if the deadline is tight and R2 may still require API or behavioral changes before final
    submission; however, if the API and contract are settled before tagging, v1.0.0 is
    acceptable per constitution 9.2 (never retag—increment patch if needed).
 ●​ Q7 (Float comparison rule — §7 rule without reproducing R's partial sort): Agree
    with the recommendation. Replicating R's internal partial-sort order adds coupling for a
    ~4.7 × 10^-16 difference; using the §7 rule with a tolerance test (1e-14 * mean(|kept|)) and
    exact checks on integer/untrimmed/asymmetric cases is clean and verifiable.
